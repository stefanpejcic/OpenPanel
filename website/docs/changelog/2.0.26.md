### 💎 New Features
- New installations and new accounts run PHP on the new [`openpanel/php-fpm`](https://github.com/stefanpejcic/php-fpm) images instead of `shinsenter/php`. PHP-FPM starts in under a second instead of 3-5 seconds, with no ownership fix, cron or startup hooks. The images are smaller (70-90 MB download) and built for amd64 and arm64. They are rebuilt every night with the latest PHP patch release and Debian security updates, and every PHP version from 5.6 to 8.5 is available with the same extensions, ionCube loader, WP-CLI and extension installs as before. The PHP-FPM pool is sized from the container's memory limit. Existing accounts keep their current images.
- New accounts: the webserver (nginx, Apache, OpenResty) reaches PHP-FPM over a unix socket (`/run/php/php-fpm-X.Y/www.sock`) instead of TCP port 9000. Each request skips the TCP round trip, about 1-2 ms faster on light PHP requests. Existing accounts stay on port 9000, and any account can be switched with `opencli php-listen <user> socket|port`.

### 🐛 Bug Fixes
- `opencli php-listen` emptied every domain's vhost when switching between port and socket, so the sites showed the webserver's default page.
- OpenPanel > PHP > Domains showed no PHP version for domains that use the PHP-FPM socket, and the WordPress opcache status couldn't reach PHP-FPM on a socket.
- Varnish: error responses (5xx) are no longer cached. After a reboot nginx can come up before PHP-FPM, and the 502 it returned in those few seconds was cached for an hour (plus 6 hours of grace) and served to every visitor even after PHP was running. Varnish now never caches a 5xx, and when a background refresh fails it keeps serving the last good copy. Applies to new Varnish installs, an existing site picks it up after its `default.vcl` is updated.
- `opencli domains-add`, `docker-hosts`, `docker-update`, `php-listen`, `user-check`, `user-litespeed` and `user-unsuspend` now point Varnish at the webserver's new IP after they restart or recreate the webserver (nginx, apache, openresty, LiteSpeed). Varnish looks up the webserver's IP only when it starts, and the webserver gets a new IP every time it starts, so pages not in the cache returned 503 until Varnish was restarted. The VCL is reloaded live with the new IP, so the cache is kept and the site doesn't go down; Varnish is restarted only if the reload fails.
